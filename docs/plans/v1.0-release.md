## Publication checklist

1. Merge the [changelog](../../CHANGELOG.md) and [known limits](../known-limits.md). Keep [#199](https://github.com/pmoreiracc/o-harness/issues/199) deferred while the observed discrepancy is limited to the design checkbox. Revisit if it affects task selection or recovery. Track [#223](https://github.com/pmoreiracc/o-harness/issues/223) through [#225](https://github.com/pmoreiracc/o-harness/issues/225) after v1.0.
2. Review the release evidence and remaining limits. Hold publication for an established defect that blocks a supported release workflow. The extended live catalog is supplemental to the release checks.
3. After maintainer approval, the repository owner starts the Release workflow on `main` with version `1.0.0`. It verifies the exact package across Linux, macOS and Windows before publishing. Check the tag, GitHub release and Claude and Codex marketplace versions after it finishes. Use standard public runners for release checks and self-hosted runners for private test fixtures so Actions compute costs stay at $0.

For future releases, use a `## vX.Y.Z` heading in `CHANGELOG.md` for the version's
release notes. The Release workflow reads that section from the commit it publishes.
When a version has no changelog text, the workflow uses GitHub's generated notes.
